# Relay (relay-worker)

Loaded only when working in this folder. Client-side protocol details are in `web/src/lib/CLAUDE.md`.

- One `Room` Durable Object per room name relays WebSocket frames (hibernation API, size cap, origin allowlist). It never logs content: the only logging is error text from failed sends.
- **Membership:** the room name in the URL is `base64url(SHA-256(token))`. A socket counts as a member only after `hello {role, token}` whose token hashes to its room name (checked in `webSocketMessage`, no stored state, no trust-on-first-use). Before that it is ignored: it gets no broadcasts, its frames aren't forwarded, it can't ack or collect anything. A bad hello closes the socket with 1008.
- **Held messages (the only thing ever stored):** a client frame starting `{"type":"msg"` is an end-to-end encrypted text envelope (the relay can't read it; it only reads `id`). It is forwarded to members of the other role and ALSO stored in the room's SQLite storage (`q` table, primary key `(id, to_role)`, `INSERT OR IGNORE` so a re-sent id can't reset the clock or replace anything) until that role sends `qack {id}`, then deleted. Rows older than `HOLD_MS` (default 30 min) are purged lazily and by a Durable Object alarm. The sender is told: `queued {id}` if it is held and no member of the other role is connected; `rejected {id,reason:"queue-full"}` whenever it could NOT be held (queue full: 50 items / 4 MB), even if a receiver looks connected, because a dead-but-not-yet-noticed socket would otherwise swallow it silently; `delivered {id}` when the receiver's `qack` actually deleted a waiting row. A `qack {id, drop:true}` (the receiver couldn't read it) tells the sender `rejected {reason:"unreadable"}` instead of delivered. A qack for an id that isn't waiting tells nobody. Unacked rows are redelivered, in order (`ORDER BY ts, rowid`), on the receiver's next `hello`. Only the receiving role's `qack` deletes a row. Never store anything else, never store plaintext, never log a body.
- **Sockets that never say hello** are closed by the same alarm after `HELLO_TIMEOUT_MS` (default 10 s); closing or erroring an unauthenticated socket does not broadcast presence. The client only treats a connection as open (and only sends) after the relay's first `presence` frame, because frames sent before the async hello verification finishes are ignored.
- Reserved frames: `presence`, `queued`, `delivered`, `rejected` are only ever sent by the relay; client frames of those types are dropped. `hello`, `msg` and `qack` are consumed by the relay (`msg` is also forwarded). `ping` -> `pong` is auto-answered. Everything else (acks, file control, binary chunks) is forwarded verbatim to the other members and not stored.
- Presence = number of distinct roles among members (0-2), so ghost sockets and second tabs don't read as a peer.
- Relay `close` handshakes are flaky (about 1 in 10 never complete, also on the deployed Worker). It doesn't affect relaying; the smoke tests use `--test-force-exit` for that reason.
- Dev: `npm run dev` (ws://localhost:8787). Typecheck / smoke test: `npm run typecheck` / `npm test` (needs `npm run dev` running, or `RELAY_URL=wss://tunnel-relay.govindplal.workers.dev npm test` against the deployed Worker). The expiry and hello-timeout tests only run against a relay started with short timers: `npx wrangler dev --var HOLD_MS:2000 --var HELLO_TIMEOUT_MS:1500` and `RELAY_HOLD_MS=2000 RELAY_HELLO_MS=1500 npm test`. When stopping a local dev relay, kill the process listening on the port and its parent by PID (never by a name pattern: that has closed unrelated terminals). Deploy: `npm run deploy` (needs `wrangler login`).
- Legacy FastAPI/Redis prototype in `../relay/` is OBSOLETE (no membership check, incompatible protocol), kept only until removed.
